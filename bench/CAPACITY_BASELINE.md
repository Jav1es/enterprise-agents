# 零成本容量测试基线（2026-10-08 修订版）

> 修订原因：上一版容量数字建立在「无 LLM、无 Redis」的降级路径上，
> 测的是 503 快速返回（P50≈1ms），**不代表真实系统容量**。
> 本版用两个零成本方案补齐依赖，测出完整编排的真实曲线。
> 全程零计费。

---

## 零、先说清上一版数字为什么作废

上一版（`ARCH_BOTTLENECK.md` 里的 112.93 req/s）测的是：

- **无 LLM Key** → `ChatOpenAI` 构造失败 → `workflow=None` → `/v1/chat` 直接 503
- **无 Redis** → 每请求连接超时重试

也就是说，那组数字是「路由 + 降级路径」的容量，编排根本没执行。
拿它当「系统容量」对外说是不诚实的。

本版补齐两项依赖后重测，得到下述真实数字。

## 一、两个零成本依赖

| 缺什么 | 补法 | 成本 |
|---|---|---|
| Redis（记忆层） | `bench/mini_redis.py` —— 纯标准库实现的极简 RESP 服务器 | 0 |
| LLM（推理层） | `src/enterprise_agent/llm/stub.py` —— 离线路径模型，`EA_STUB_LLM=1` 启用 | 0 |

### mini_redis
支持 GET/SET/DEL/EXISTS/EXPIRE/TTL/INCR/HSET/HGETALL 等常用命令。

⚠️ 踩坑：`redis-py` 8.x 默认 RESP3，连上先发 `HELLO` 握手，不实现会超时
（`redis.exceptions.TimeoutError`）。实现握手后仍有问题，
最终让 `ShortTermMemory` 显式降级到 RESP2 —— 本类只用 get/set/delete，
RESP3 特性用不上，RESP2 兼容性最好。

### StubLLM
走完整 LangChain `BaseChatModel` 契约，固定输出、零网络。
带 ~2ms 模拟延迟，**避免「零成本模型」把编排开销测得过轻**。

`/health` 暴露调用次数，可确认编排真的执行过：

```json
{"workflow":"ready","llm":{"mode":"stub","calls":184,"chars":4784}}
```

## 二、完整编排的真实容量曲线

实测：每级 20 秒，全程 **0 失败**。

| 并发 | req/s | P50 | P95 | P99 | 最大 |
|---|---|---|---|---|---|
| 10 | 13.19 | 75 ms | 790 ms | 1500 ms | — |
| **20** | **19.31** | 130 ms | 1700 ms | 1900 ms | — |
| 50 | 15.42 | 470 ms | 4200 ms | 5200 ms | — |
| 100 | 15.28 | 640 ms | 7900 ms | 8600 ms | — |

### 饱和点在 20 并发

| 区间 | 吞吐变化 | 增幅 |
|---|---|---|
| 10 → 20 | 13.19 → 19.31 | **+46.4%** |
| **20 → 50** | 19.31 → 15.42 | **−20.1%** ⚠️ |
| 50 → 100 | 15.42 → 15.28 | −0.9% |

**并发从 20 翻到 50（2.5 倍），吞吐不升反降 20%，P95 从 1.7s 涨到 4.2s。**
再往上（100 并发）吞吐完全持平，P95 达 7.9s。

⇒ **单实例舒适区 = 20 并发 / 约 19 req/s**，超出即进入排队延迟区间。

### 分端点（并发 20）

| 端点 | 请求数 | 失败 | 平均 | P95 |
|---|---|---|---|---|
| `GET /health` | 260 | 0 | 114 ms | 320 ms |
| `POST /v1/chat` | 184 | 0 | **942 ms** | 1600 ms |
| `POST /v1/chat/stream` (SSE) | 88 | 0 | **119 ms** | 300 ms |

两个结论：

1. **同步对话 P95 约 1.6 秒** —— 这是五阶段编排（Router → Planner → Skill →
   Tool → Reviewer）+ RAG 检索 + 记忆读写的完整成本。
2. **SSE 只要 119ms** —— 因为 `EventSourceResponse` 响应头立即返回，
   生成在流里继续。**首包延迟与总生成时间解耦**，长任务场景应优先用流式。

## 三、对比：路由路径 vs 完整编排

| 场景 | 并发 20 吞吐 | `/v1/chat` P95 |
|---|---|---|
| 降级路径（无 LLM/无 Redis） | 39.94 req/s | 1 ms（直接 503） |
| **完整编排（StubLLM + Redis）** | **19.31 req/s** | **1700 ms** |

**吞吐差 2 倍、延迟差 1700 倍。** 这就是为什么「在降级路径上压测」毫无意义 ——
它测的是一个只会返回 503 的服务。

## 四、Locust 口径修正（重要）

离线降级时 `/v1/chat` 返回 503 是**预期的正确行为**，但原脚本把它记作失败，
导致离线压测出现 **~50% 假失败率**（实测踩过），反而掩盖真实吞吐。

⚠️ 关键坑：Locust 里**「不调用 `failure()`」并不等于成功**。
只要响应码非 2xx 且没有显式 `r.success()`，仍会被计为失败。
必须显式调用：

```python
if r.status_code == 503:
    r.success()   # 离线降级，预期行为
```

修正后：9410 请求 0 失败。

## 五、这轮拿到的部署结论

| 配置 | 值 | 依据 |
|---|---|---|
| 单实例舒适并发 | **20** | 实测饱和点 |
| 单实例吞吐 | **约 19 req/s** | 实测峰值 |
| `minReplicas` | 2 | 单实例扛不住高并发 |
| CPU HPA 阈值 | 70% | 编排吃 CPU，留余量 |
| `maxReplicas` | **≥ 5** | 100 并发需约 5 实例（100÷20） |
| 响应策略 | **长任务走 SSE** | 首包 119ms vs 同步 1.6s |

## 六、复现（全程零计费）
