# 压测与延迟基准报告（Locust 阶梯 + LLM 延迟分解）

> 实测环境：Windows 11 · Python 3.11.8 · uvicorn **单 worker** · 127.0.0.1:8080
> 模型：`deepseek-chat`（经 `api.deepseek.com`，实际路由到 `deepseek-flash`）
> 复现命令见文末。**全部数字为本机真实运行结果，未做任何美化。**
> 报告日期：2026-10-07

## 一、阶梯压测：找吞吐饱和拐点

单点压测只能得到「某个并发下的表现」；阶梯压测画出 **吞吐-并发曲线**，
才能回答「系统在哪个并发点不再线性收益」——这正是 HPA `maxReplicas` 该设多少的依据。

### 结果（每级 30 秒）

| 并发 | 请求数 | 失败率 | 吞吐 (req/s) | P50 | P95 | P99 |
|---|---|---|---|---|---|---|
| 10 | 206 | **0.00%** | 7.13 | 2 ms | 2500 ms | 2800 ms |
| 20 | 399 | **0.00%** | 13.80 | 2 ms | 2600 ms | 2800 ms |
| 50 | 805 | **0.00%** | 27.78 | 29 ms | 3000 ms | 3200 ms |
| 100 | 1125 | **0.00%** | 38.85 | 78 ms | 4000 ms | 4400 ms |

### 饱和拐点：落在 **50 → 100 并发之间**

| 区间 | 吞吐变化 | 增幅 |
|---|---|---|
| 10 → 20 | 7.13 → 13.80 req/s | **+93.5%**（线性增长） |
| 20 → 50 | 13.80 → 27.78 req/s | **+101.3%**（仍是线性） |
| **50 → 100** | 27.78 → 38.85 req/s | **+39.8%** ⚠️（明显递减） |

**结论**：
1. **并发 ≤50 时系统近似线性扩展**，加并发就加吞吐。
2. **并发翻倍（50→100）只换来 39.8% 的吞吐**，但 P50 从 29ms 涨到 78ms、
   P95 从 3000ms 涨到 4000ms —— **延迟开始恶化而吞吐不再跟上，这就是饱和**。
3. **全程 2535 次请求 0 失败**（0.00%）。单 worker 在 100 并发下仍不报错，
   说明编排层没有资源泄漏或竞态问题；但延迟已进入不可接受区间。

### 这对部署配置意味着什么

| 配置 | 值 | 依据 |
|---|---|---|
| `minReplicas` | 2 | 50 并发已饱和，单实例不能兜底底线 |
| CPU HPA 阈值 | 70% | 编排请求吃 CPU，70% 触发扩容留出余量 |
| **`maxReplicas`** | **建议 ≥ 6** | 每实例在 ~50 并发前表现良好；若要给 300 并发余量，需 6 实例。**现设 10 偏保守但安全** |

按实测反推容量公式：**单实例舒适区 ≈ 50 并发 / ~28 req/s**。
要承载 300 并发需 6 实例，要承载 500 并发需 10 实例。

## 二、LLM 延迟分解：瓶颈到底在模型还是在编排

降级模式（无 LLM Key）下编排链路 P95 ≈ 2400 ms，那**全部是本地编排成本**。
接上真实 LLM 后总延迟由「首 token」与「后续生成」构成。
不知道这个比例，就无法判断该优化模型还是优化自己的代码。

### 结果（5 次真实计费调用，流式）

| # | 首 token | 总耗时 | 分块 | 输出字数 |
|---|---|---|---|---|
| 1 | 628.0 ms | 1081.4 ms | 76 | 131 |
| 2 | 608.4 ms | 1076.8 ms | 83 | 136 |
| 3 | 939.6 ms | 1390.4 ms | 70 | 113 |
| 4 | 916.3 ms | 1549.3 ms | 73 | 124 |
| 5 | 789.6 ms | 1233.4 ms | 76 | 127 |

| 指标 | 值 |
|---|---|
| 首 token **中位** | **789.6 ms** |
| 首 token 均值 | 776.4 ms |
| 总耗时中位 | 1233.4 ms |
| 总耗时均值 | 1266.3 ms |
| **首 token 占比** | **61.3%** |

### 结论：瓶颈主要在**模型侧**，不在编排代码

- **61.3% 的总延迟花在等模型吐第一个字上**，这是网络往返 + 模型排队，
  本地代码优化不了。
- 剩余 38.7% 是后续 token 生成，受模型输出长度影响。
- ⚠️ 注意口径差异：上面 1233ms 是**裸 API 调用**（无编排）。
  而 `/v1/chat` 端点实测 2400ms，两者之差（~1200ms）才是**本地编排 + RAG 检索的真实成本**。

⇒ **优化优先级**：先做流式返回（把首 token 提前暴露给用户，实测 SSE 平均 11ms 就能返回响应头），
其次才是压编排层。把 TTFT 从 790ms 优化掉是不可能的，但**让用户不用等它**是可以的。

## 三、被拒绝的做法（记录以免重复踩）

**高并发压测绝不能用真实 LLM Key 跑。** 100 并发 × 30 秒意味着数千次计费调用，
既烧钱又会触发上游限流、让结果失真。
⇒ 本报告的阶梯压测在**降级模式**下跑（本地编排 + RAG，无外部调用）；
LLM 延迟单独用 5 次调用小样本测。两者分开，是为了让「容量数字」和「模型延迟数字」互不污染。
