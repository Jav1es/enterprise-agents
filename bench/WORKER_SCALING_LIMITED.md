# 多 worker 横向扩展：结论是「测不出来」，而不是某个数字

> 这份报告的结论可能让人失望，但比给一个假数字诚实。

---

## 一、为什么作废之前的多 worker 结论

`ARCH_BOTTLENECK.md` 里写过「多 worker 变慢，扩展效率仅 6-15%」。
**该结论作废** —— 那次测的是降级路径（`/v1/chat` 直接 503），编排没执行。

补齐 StubLLM 与 mini-redis 后重测，两轮结果**互相矛盾**：

| 并发 20 | 1 worker | 2 workers | 4 workers |
|---|---|---|---|
| 第 1 轮（25s） | 17.81 | 10.48 | **39.06** |
| 第 2 轮（25s） | 11.16 | 9.21 | **10.31** |

**同一个配置（4 worker），两轮相差 3.8 倍。**
当重复测量之间差异大于配置之间的差异时，任何「扩展效率」都是噪声的产物。

---

## 二、噪声来源（已定位）

### 主要：系统后台负载

```
ProcessName    Id      CPU秒    内存MB
SetupHost    20148   1497.00    60.00   ← Windows 安装程序，持续吃 CPU
WorkBuddy    28412    295.00   433.00
Marvis       11692    226.00    53.00
CefRenderer  12416    136.00   878.00
```

`SetupHost` 是**系统安装进程，不属于本任务，不能也不该杀**。
它在压测期间持续占用 CPU，直接污染所有吞吐数字。

### 次要：测量环境本身

- **压测客户端与服务端同机** —— Locust 本身要吃 CPU，与被测服务争抢同一批核心；
  并发越高，客户端占用越明显。
- **Chroma 缓存命中** —— 观察到连续相同请求时 `/v1/chat` 从 990ms 掉到 19ms，
  说明检索层有缓存。这让「重复问题」比「新问题」快得多，抬高并打乱吞吐。

### 已排除

- 残留 uvicorn/locust 进程（已按端口精确清理，改用 `kill_stale_on_port`）
- 真实 LLM 调用（stub 模式，零计费）

## 三、能确定的部分

### 1. 单实例饱和点在 20 并发（这个结论稳）

`CAPACITY_BASELINE.md` 的阶梯测试，四级全程 0 失败，趋势清晰：

| 并发 | req/s | P95 |
|---|---|---|
| 10 | 13.19 | 790 ms |
| 20 | 19.31 | 1700 ms |
| 50 | 15.42 | 4200 ms |
| 100 | 15.28 | 7900 ms |

**并发翻 2.5 倍吞吐反降 20%** —— 这个反转幅度远超噪声范围，结论成立。

### 2. 编排是 async I/O 为主，横向扩展收益有限

从数据看：1→4 worker 吞吐没有稳定提升（两轮分别是 +119% 和 −8%）。
若编排里有大量 CPU 计算，横向扩展应该显著；没有提升说明瓶颈不在单进程 CPU，
而在 **共享的外部资源**（Chroma 的 SQLite 文件锁、Redis 连接池）或 **本机 CPU 已被后台占满**。

**在 `SetupHost` 停止之前，无法区分这两种原因。**

## 四、要得出可信结论，需要满足的前提

1. **干净的机器**：无 `SetupHost` / 安装程序 / 其它重负载
2. **压测客户端分离**：Locust 跑在另一台机器或至少绑定到独立核心
3. **每次配置重复 ≥5 轮取中位数**，并报告标准差
4. **知识库非空**：当前 Chroma 集合为空，缓存命中行为不真实

第 1 条当前无法满足 —— 那需要等用户的系统安装完成。

---

## 五、现在能给的部署建议（保守）

在拿到干净环境数据之前，不宣称「N 个 worker 能撑 M 并发」，只给确定的部分：

| 结论 | 依据 | 置信度 |
|---|---|---|
| 单实例舒适区约 20 并发 / 19 req/s | 阶梯测试，四级 0 失败，转折清晰 | **高** |
| 并发 >50 时 P95 必然恶化（>4s） | 阶梯测试一致 | **高** |
| 长任务必须走 SSE（首包 119ms vs 同步 1.6s） | 分端点实测 | **高** |
| 多 worker 能提升编排吞吐 | **无证据** | **不成立** |
| HPA maxReplicas = 5 | 基于「单实例 20 并发」外推，未验证 | **低（待验）** |

⚠️ Helm Chart 里的 `maxReplicas: 10` 目前**没有实测支撑**，只是保守设定。
真要对外说这个数，得先拿到干净环境的对比数据。
